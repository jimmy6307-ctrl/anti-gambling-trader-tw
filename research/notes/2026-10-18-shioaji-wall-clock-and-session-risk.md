## New primary-source clarification — distinguish wall-clock encoding from a true UTC epoch

Sinotrade's official `plugins/shioaji/skills/shioaji/references/MARKET_DATA.md` at `master` (blob SHA `c3303fee797bbff0aca798d7c594c760376129a3`) explicitly states that historical Shioaji Python `api.ticks().ts` and `api.kbars().ts` nanoseconds encode **Taiwan market wall-clock**; decode with `pd.to_datetime(ts)` (or Polars ns cast), **do not treat as UTC and do not add eight hours**. If timezone-aware values are needed, `tz_localize("Asia/Taipei")` without clock shift. This guidance is scoped to market-data timestamps, not order/deal/account records. Source: https://github.com/Sinotrade/Shioaji/blob/master/plugins/shioaji/skills/shioaji/references/MARKET_DATA.md

This explains why the tutorial's `1779094808306075000` displays `2026-05-18 09:00:08.306075`, whereas interpreting the same bits as an actual UTC epoch and converting to Taipei gives 17:00:08. The existing `tw_shioaji_timestamp_gate.py` flags this as `EIGHT_HOUR_AMBIGUITY_OR_DOCUMENTATION_MISMATCH` based on UTC-epoch arithmetic. **The documentation now explicitly explains the intended market-data encoding**, but this is documentation-level resolution only: installed API version, real response and official session reconciliation remain unverified.
